# 工程环境体检与改造

## 读取顺序

检查项目指令、工作区状态、构建/启动入口、锁文件、CI，再抽样一个正常模块和一个问题模块。确认命令确实存在，不假设所有项目都使用 pnpm、React 或某种测试工具。

记录每项为 `observed`（已看到或执行）、`missing`（确认缺失）、`unknown`（无法判断）。证据必须能定位到文件、命令结果或真实运行记录；不要从“存在测试目录”推断测试有效。

| 维度 | 实际核查 | 缺口造成的问题 |
| --- | --- | --- |
| 范例质量 | 当前模块附近有无清楚、可运行、无过时模式的实现 | Agent 复制坏模式 |
| 类型与边界 | 外部输入校验、依赖方向、共享契约是否有机器约束 | 错误只能靠人解释 |
| 开发环境 | 安装、启动、健康检查是否有确定入口 | Agent 无法独立验证 |
| 数据与隔离 | 可重置样本、测试身份、并行运行端口 | 结果互相污染或不可重现 |
| 测试有效性 | 关键行为有断言；已知错误能使检查失败 | CI 绿色但功能坏掉 |
| 产品证据 | 真实 UI/API/CLI 路径能否运行并保存证据 | 只能阅读实现猜测正确 |
| 反馈沉淀 | 重复 review 纠错是否对应可执行约束 | 同一种错不断返工 |
| 交付控制 | 相关必需 CI、权限边界、回退路径和异常反馈 | 自动化放大缺陷 |

## 排序与实施

按“影响 × 重复发生概率 × 能否可靠自动检查”判断价值，再估计实现和维护成本。没有可信数据就用高/中/低并解释，不编造精确分数。

选择最多三项近期改进：

1. 先消除当前任务无法验证的阻塞。
2. 再解决高频错误的根因与坏示例。
3. 再提高执行速度和并行容量。

为每项明确：问题证据、最小改动、验证方式、完成条件、可逆路径。`audit` 只输出；`harden` 在授权范围内实际实施最高价值改进。

## 历史代码整理

先建立现有行为基线，分清应该保留的兼容行为与需要修正的缺陷。依次收拢重复实现、隔离旧接口、让新路径使用清晰 API，再在有引用证据和测试保障时移除死代码。

不要进行没有验收条件的全量重写。行为修复与纯结构变更尽可能分离，便于定位回归；保留与本次任务无关的用户改动。

## 项目验证契约

用 `assets/verification-contract.template.md` 固定启动和验证入口。以真实项目命令填充，实际跑通后才标记可用。保留证据目录，清理临时环境。

不要在 AGENTS.md 里重复整个契约。保留入口与关键约束，让机器检查承担可执行部分。
