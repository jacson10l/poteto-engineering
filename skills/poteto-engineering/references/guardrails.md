# 将纠错变成机器约束

## 选择最靠近根因的一层

| 纠错类型 | 优先机制 | 验证机制有效 |
| --- | --- | --- |
| 不合法状态、缺少必需字段 | 类型、构造函数、状态联合类型 | 合法构造通过，非法构造失败 |
| 外部输入不可信 | 边界解析与运行时校验 | 错误、缺字段、边界输入被拒绝，合法输入保留 |
| 危险用法或废弃调用 | 现有 Lint 规则或窄范围自定义规则 | bad/good fixture，明确报错位置与替代写法 |
| 依赖方向或分层越界 | import boundary/依赖图检查 | 直接与适用的间接越界路径均能被检测 |
| 明确业务回归 | 行为测试、契约测试 | 缺陷版本失败，修复版本成功 |
| 并发与重试不变量 | 属性测试、模型检查、运行时断言 | 反例被发现，边界和假设有记录 |
| API 容易误用 | 重新设计 API、缩小能力范围 | 正常使用简单，错误组合无法表达或立即报错 |
| 主观外观、业务取舍 | 小量说明与实际产品检查 | 真实用户路径和可比较证据 |

不要机械规定每次纠错都新增一条 Lint。检查既有规则能否覆盖；优先修根因，避免数十条相互冲突的补丁规则。

## 规则落地步骤

1. 描述一个具体错误和一个合法反例，确认规则不是个人偏好。
2. 在最窄且稳定的范围实现；复用项目已有设施。
3. 运行坏例子和正常例子，确认报错清晰且可采取行动。
4. 对受影响代码评估误报；整合到现有本地/CI 命令。
5. 处理已有违规：新代码先受约束，历史基线逐步减少。基线必须可追踪，不能自动扩大。
6. 只有确实需要的例外才能有窄范围豁免、理由和跟进；不要默认全局 ignore、any、ts-ignore 或关闭测试。

## 技术栈适配示例

以下是适配思路，不是默认强制改造或安装依赖。

- **Vue 3 + TypeScript**：业务状态优先用可区分的联合类型；props、emit 与 API DTO 保持一致；按现有项目使用 `vue-tsc` 或等效检查。类型不能替代 HTTP/IPC 等外部输入的运行时校验。
- **Element Plus 表单**：覆盖提交、校验失败、重复点击、请求失败后的状态恢复；不仅检查按钮渲染出来。
- **Electron**：明确 renderer、preload、main 的依赖方向；渲染层通过最小 IPC API 请求能力；校验消息和来源；约束对 privileged API 的直接导入。
- **Tauri**：复用现有 capabilities 与命令边界，前端数据仍按不可信输入处理；检查前后端契约和错误路径。
- **React**：团队反复误用 Effect 时，先区分必要副作用与派生状态，再选择 API 重构或局部限制。不要把别的团队的 useEffect 禁令推广成所有项目通则。
- **任务/交易类服务**：以幂等键、重复事件、过期结果和重试边界为测试对象；验证使用模拟/隔离环境，不能因启用本 skill 就访问真实账户或下单。

## AGENTS.md 最小职责

保留现有文件有效指令，并在用户授权的整理中去除已经完全被工具覆盖的重复解释。合理内容为：项目/模块导航、实际命令入口、无法从源码推断的要求，以及危险操作边界。

不要设置通用行数上限，也不要把全部指令挪进一个更长的 skill 后声称减少上下文成本。参考资料按任务加载，规则尽量留在可执行工程中。
