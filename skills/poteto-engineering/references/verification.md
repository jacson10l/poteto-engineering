# 用可检查的证据证明改动

## 验证层次

| 层次 | 适用目标 | 不能证明的事情 |
| --- | --- | --- |
| 类型、Lint、架构检查 | 接口约束、明显错误、依赖边界 | 用户实际流程正确 |
| 单元/属性测试 | 局部规则与输入空间 | 集成和真实 UI 没问题 |
| 契约/集成测试 | 模块边界、状态持久化、错误传播 | 所有设备和交互都正确 |
| 真正运行产品 | 目标用户路径、显示、交互、CLI/API 行为 | 没走过的路径也都正确 |
| 模型检查/证明 | 明确形式化性质在给定语义下成立 | 需求本身正确，模型必然等于实现 |

根据风险和失败模式组合，不能用一种检查代替全部层次。对普通小改动，直接运行相关检查和查看结果即可；不要固定要求覆盖率达到某个百分比。

## 不同任务的证据

- **UI 静态/交互修复**：尽可能保存同数据同视口的前后截图；写清操作与结果；查看图片本身，检查是否空白、遮挡或截错页面。交互必须实际操作过。
- **时序/动画/跨步骤问题**：视频或 trace 展示完整触发链、结果与关键时间点；视频无法导出时可用连续截图配合事件日志并说明限制。
- **API/CLI**：记录输入、执行命令、退出码/状态码和实际输出；补充状态变化或副作用断言。不要用成功响应代替业务条件。
- **后台/并发**：确定性种子、时钟或事件序列；记录重复、乱序、失败、重试场景以及最终不变量。
- **性能**：同硬件、版本、数据和采样方法对照；给出测量次数、p50/p95 或适合该任务的统计量与噪声范围。未经测量不写“快了 X%”。

证据标明源码版本、工作区是否有未提交改动、运行环境和时间。必要时记录补丁摘要。只保存必要信息，对凭据和个人数据脱敏。

## 检查本身也要能失败

对新增重要规则/回归测试，用原缺陷或隔离的受控坏变体验证确实失败；随后在正确版本通过。坏变体不得污染交付工作区，也不能触碰用户未提交工作。

若已有测试不能在原缺陷失败，先检查断言、测试发现范围、mock 边界、错误吞没和实际执行文件。不能靠改预期输出让坏行为过关。

## 形式化验证的边界

先写用户能理解的不变量，例如“同一任务不能同时被两个有效持有者执行”，再识别状态、事件、并发、失败和时钟假设。区分安全性（坏事不会发生）与活性（好事最终发生）；后者经常需要公平性等额外假设。

- 事件交错、协议、分布式状态迁移：考虑设计模型与模型检查。
- 可约束代码的输入/执行空间：考虑代码级有界检查。
- 所有输入/规模上的性质：在工具与成本适合时采用证明；仍要明确前提。
- 没有可用验证器：实际执行属性测试/模糊测试，标注它们是测试，不能改名为形式化证明。

记录：性质、工具和版本、运行命令、代码与模型对应关系、状态/步数/输入边界、假设、结果、反例、未覆盖事项。

必须实际执行并检查完整状态。超时、未穷尽、工具错误、依赖缺失均不是通过。使用坏变体验证性质不是空泛成立或被错误假设排除。

模型反例先映射回真实代码，区分模型不准确与产品缺陷；可行时用实测复现。产品改变后更新覆盖映射并重跑，不能拿旧模型的绿色结果担保新代码。

## 证据清单校验器

`validate_evidence.py` 使用 Python 3.9+ 标准库，不执行清单中的命令。它仅检查必需条件是否有通过记录、退出码、版本标签以及已存在且哈希匹配的文件；UI 条件还要求清单声明为图像/视频/trace 的文件。

它不识别文件内容或核实清单声明的媒体类型；哈希也不能证明截图来自产品、视频内容正确或测试确实执行。Agent 仍须直接运行命令、检查输出并查看视觉证据。不能将此脚本通过描述为“程序已被证明正确”。
