# 交付、自动闭环与衡量

## 完成状态

| 状态 | 可对用户说什么 |
| --- | --- |
| verified | 验收条件由当前版本的真实检查覆盖，列出证据与限制 |
| changed-unverified | 已完成改动，但某些必需运行检查未做或受阻；不能说修复已验证 |
| failing | 必需检查仍失败；解释失败和下一步，不当成成功交付 |
| audit-only | 已完成只读评估；明确尚未改工程 |

区分历史已有失败和本次新增失败；记录基线证据。历史失败不能自动视为本次可忽略：是否阻挡交付由相关性和既有项目政策决定，必需 CI 仍须符合原门槛。

## 自主程度逐步扩大

1. 工具能在隔离环境复现一次真实任务并保留证据。
2. 多次任务稳定完成，重复错误已变成规则；仍由既有评审流程决定合并。
3. 对已有授权的低风险类别，使用分支保护、必需检查和可逆发布路径进行受控自动合并。
4. 在具备运行监测和反馈入口后，把发现、复现、修复、验证、合并和观察串成闭环。

每一步要求真实历史表现和明确范围，没有固定六个月等待期，也不能因六个月到了就自动升级权限。发现回归时收缩相关类别，补充复现与防复发机制。

启用自动化不得顺带更改保护规则、绕过失败 CI、扩大凭据权限或执行生产变更。依据会话与项目已有授权行动；没有授权时先完成可供审阅的改动与证据。

## 衡量有效产出

在相同时间窗口、仓库集合和变更口径下观察：

- 已验收且未产生已知回归的任务数，以及用户实际得到的功能/性能改善。
- 交付周期、返工次数、人工介入时间、同类问题复发率。
- 已逃逸缺陷、检查误报、flaky 测试以及修复耗时。
- 每个已验收任务的计算成本；不要直接把 Token 数量或 PR 数量当效率。

回滚率先定义“回滚”：是 revert PR、回滚部署，还是其他恢复动作。分子应为同一观察窗口和观察期内发生回退的原始变更数，分母为同口径已交付变更数。注明可能漏掉 forward-fix、尚未暴露缺陷、未达到完整观察期等情况。不要拿不同分母比较。

不设“必须 11,000 PR/月”或“必须 0.5%”为验收指标；这些数字不能代替你项目自己的质量基线。

## 简短交付格式

行为变化 → 关键实现原因 → 实际检查结果 → 证据链接 → 未覆盖事项 → 防复发规则（若有）。只报告本次确实做过的工作，缺失信息写未知。
