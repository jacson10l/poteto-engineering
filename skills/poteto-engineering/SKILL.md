# Poteto 工程闭环

让正确实现成为最容易走通的路径。把这项原则落实到代码、工具和持续集成，避免不断扩大提示词。

## 选择执行模式

从用户意图选择模式；能从项目确认的信息直接读取，不重复询问。

| 模式 | 触发意图 | 行动和交付 |
| --- | --- | --- |
| audit | 评估、体检、看看问题 | 只读审计；给出现有证据、主要缺口、优先修复项，不擅自改产品 |
| harden | 改造流程、建立约束、优化 Agent 环境 | 在授权范围内落实最高价值的环境/规则改进，并实际证明规则能抓住坏例子 |
| deliver | 实现、修复、重构 | 先定义可观察的完成条件，再改动、验证、收集证据并沉淀适量防复发约束 |

未给项目时，使用已明确选中的项目；不存在选中项目则先交付方法或询问项目位置。不得选择无关私有仓库。只做用户请求的工作，不因本 skill 自动重写整个工程。

## 执行顺序

### 1. 建立基线与验收条件

- 读取适用的项目指令、工作区状态、入口、依赖锁定文件、现有脚本和 CI。
- 把请求转为 1–5 条可观察条件：具体输入、操作、预期结果、边界。区分外观、功能、性能和不变量。
- 标记目标版本与已有改动，保留用户工作；基线运行选择与任务相关的最小检查集。
- 对 bug 先尝试复现并保留失败证据。无法复现就记录尝试、环境和限制；不能把猜测改动宣称为已验证修复。
- 给出一次简短判断：能直接实施，还是需先修复哪个局部验证阻塞。不要把每个任务变成全项目体检。

### 2. 修正会诱导 Agent 的工程环境

- 找一个经过验证的正常实现作为范例；不要以“旧代码就是这样写的”证明合理性。
- 对当前范围中的重复补丁、过时接口、含混类型和越界依赖，优先做小范围且可验证的整理。
- 将可重复且能准确检测的纠错放入类型、API、Lint、架构检查或测试；先寻找既有规则，避免重复造轮子。
- 为新增约束提供坏例子和正常例子，验证前者失败、后者通过，再纳入现有检查入口。无法机器判定的要求才留短说明。
- 历史债务分步收敛，新增代码不能继续扩大已知问题；不要为了变绿删断言、降低类型检查或批量加忽略。
- 仅保留 AGENTS.md 中必要的命令入口、目录边界和不可推断约束；遵守仍然有效的现有指令，不机械删除它们。

### 3. 补齐自我验证工具

- 复用工程现有能力，建立确定的启动、健康检查、操作、证据采集、清理路径。
- 优先使用可复现数据、测试身份、确定性随机种子和隔离端口；需要时提供少量可组合的 CLI 命令及结构化输出。
- 运行一次真实路径以证明工具可用。空测试套件、未实际运行的脚本、只返回 200 的空接口均不能证明功能正确。
- 启动的进程由本任务追踪并清理；证据保留在清理范围之外。不终止不属于本任务的进程。

### 4. 实施并按风险验证

- 保持改动集中，先运行便宜且相关的检查，再覆盖集成与真实使用路径。
- 对 bug 保留能在原实现失败、修复后通过的回归检查；无法可靠做到时明确原因和剩余风险。
- UI 修复须实际运行、检查交互，并提供真实截图；时序、动画、拖动等问题优先视频或可回放 trace。不能用生成图、设计稿或文字解释冒充运行证据。
- API/CLI/后台任务使用输入输出、状态变化、结构化日志和断言作证，不强制无意义的截图。
- 性能结论使用同环境、同工作负载的前后测量，记录采样次数、波动和资源开销，不能用一次成功推断普遍提升。
- 并发、重试、状态迁移和关键不变量有必要时增加属性测试、模糊测试或模型检查。实际运行验证器后才能声称通过；记录模型假设、边界、对应代码版本和不覆盖内容。
- 普通文本/样式等低风险调整采用直接检查；不要强制增加镜像实现的单测、形式化模型或多轮抽象审查。

### 5. 交付证据，防止复发

- 将每条验收条件关联到真实检查和证据；写明实际执行、失败、未执行和受阻的项。
- 代码验证后若再次变化，重新运行受影响检查，不能沿用不对应当前版本的证据。
- 只有相关必需检查通过、证据可查看，才报告已验证完成；缺少执行环境时报告“改动完成，运行验证受阻”，继续完成不依赖该环境的工作。
- 如纠错揭示稳定通用的规则，落入适当检查层；一次性业务例外不强行泛化成全局禁令。
- 交付包含：行为变化、关键原因、验证结果及证据链接、剩余限制、此次新增的防复发机制（若有）。不以长篇说明替代证据。
- 大型或多条件任务可复制 `assets/evidence.template.json` 并运行 `python3 <本 skill 目录>/scripts/validate_evidence.py <manifest.json>`。小任务用等价简短记录即可；此脚本只检查清单与文件一致性，不能认证证据真实性，也不是合并许可。

## 自动闭环与 Token 分配

先复现，再修复，再验证，再考虑合并与监测。自动合并只使用现有授权、分支保护、必需 CI 和项目政策；本 skill 不授予合并、部署、访问生产或交易的权限。不要为已授权的常规操作重复征求批准。

只有连续真实任务验证了工具和门槛可靠性，才逐步扩大自主范围。检查能力不足或出现反复回归时，缩小自动化范围、修补工程环境。不要将 PR 数量、Token 消耗或模型赞同数当作质量目标。

把额外计算投入可检验的不确定性：执行测试、复现边界、检查真实产品和高价值不变量。通过且无新证据时结束检查；遇到重复失败先定位根因，不盲目追加 Token 或审查轮次。
